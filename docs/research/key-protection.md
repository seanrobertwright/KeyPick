# Per-decryption key protection for age identities

Research for issue #25, a child of the wayfinder map (#9). It feeds the decision ticket #26, "How is each machine's age key protected so decrypting needs approval?". It builds on the approval-gating research for issue #10 (branch `research/approval-gating`, file `docs/research/approval-gating.md`) and does not repeat it. Researched 2026-10-10. Star counts and release dates are as of that day.

## Question

Which age plugins or OS keystores can make each decryption of the vault require the user's presence, on Windows, macOS, Linux, and WSL? For each mechanism: which platforms it supports, whether presence is required on every decryption or cached (and for how long), how mature and maintained it is, how hard it is for a stranger to install, whether the key can be exported, and what it means for KeyPick's recovery key, for adding a new machine, and for the GitHub Actions re-encryption workflow. Also: how SOPS consumes age plugins and `SOPS_AGE_KEY_CMD`.

## Summary

- **Only three mechanisms put a presence check on every decryption today, and each covers part of the platform matrix.** age-plugin-se (macOS, Touch ID or passcode, no cache), age-plugin-yubikey with touch policy `always` (Windows, macOS, Linux, and WSL through the Windows binary), and FIDO2 `hmac-secret` plugins (Linux and macOS; Windows needs administrator rights). age-plugin-tpm needs a TPM PIN at most, which is knowledge, not presence, and it runs on Linux only. DPAPI and a plaintext `keys.txt` gate nothing against a same-user process.
- **No age plugin uses Windows Hello.** None appears in the awesome-age list or in GitHub searches. The building blocks exist: `KeyCredentialManager` keys and decrypt-capable keys in the Microsoft Passport key storage provider, which KeePassWinHello and the ByteNess keyring fork already use. KeyPick would have to write and ship the plugin itself. Whether Windows caches a Hello gesture for later key operations is still undocumented.
- **What one approval releases differs, and it matters more than the prompt.** With the Secure Enclave, a YubiKey's PIV slot, a TPM, or a Passport decrypt key, the private key stays in hardware, and one approval yields one wrapped file key: for SOPS, the data key of one vault file. With FIDO2 `hmac-secret`, a Hello signature used as a wrapping key, a `SOPS_AGE_KEY_CMD` helper, or a passphrase-encrypted identity, one approval yields the *long-term* age identity to whichever process asked. A single mistaken approval then compromises every past and future file.
- **SOPS supports all of this from 3.10.0 (2025-03-30).** That release added age plugins, `SOPS_AGE_KEY_CMD`, and passphrase-protected identities. Plugin recipients go in `.sops.yaml` like any `age1...` key, and plugin identities (`AGE-PLUGIN-...`) go in the identity file. KeyPick pins SOPS 3.9.4 in setup (`SOPS_VERSION` in `ts/src/commands/setup/prerequisites.ts`) and 3.9.1 in the vault-sync workflow, both of which reject plugin recipients.
- **Every machine that encrypts must be able to encrypt to every plugin recipient.** That includes CI, which runs `sops updatekeys`, and any machine running KeyPick's `save()`. Each needs the matching plugin binary on `PATH`, unless the plugin emits age's new native `age1tag1...` recipients. SOPS does not yet parse `age1tag1` natively (open PR getsops/sops#2266), so today it still needs a small `age-plugin-tag` binary from age's `extra/` directory.
- **The CI key stays a no-presence path to every secret.** `sops updatekeys` has to decrypt each data key, so the GitHub Actions identity can read everything, and GitHub says any user with write access to the repository can read its secrets. Per-machine presence does not cover CI unless the secret is gated (for example, an environment with required reviewers) or CI re-encryption is dropped.
- **Hardware-bound keys change recovery and onboarding.** Secure Enclave, TPM, and Hello keys can't be exported or copied to a new machine, so the software recovery key stays essential and every new machine needs a re-wrap. A YubiKey or FIDO2 token is the exception: the same token works on every machine, so adding a machine needs no re-encryption.
- **WSL can reach a Windows-side key in two ways.** It can run the Windows plugin binary through interop, which age-plugin-yubikey documents. Or it can pass the USB token into WSL with usbipd-win. A TPM is not exposed to WSL2 at all.

## How to read "presence" here

The approval-gating research established that only a per-use operation gated by hardware or the OS holds up against a same-user process. This note sorts mechanisms by two properties.

1. **Is a human gesture needed for each decryption?** "Presence" means something an agent can't do from the keyboard: a fingerprint, a face, a physical touch, or a PIN typed into an OS or hardware prompt. A PIN or passphrase is *knowledge*. An agent can't type it unless the user hands it over (for example in an environment variable), but it isn't proof that the user is physically present.
2. **What does one approval release?** Either one wrapped file key (the private key stays in hardware), or the long-term age identity (a software key gets unwrapped into the caller's memory).

None of these mechanisms tells the user *who* asked. A rogue `sops -d` makes the same plugin raise the same prompt that KeyPick would. KeePassWinHello's own security notice tells users to cancel any Hello prompt they did not start, "just like you cancel an unintended UAC dialog" ([KeePassWinHello README](https://github.com/sirAndros/KeePassWinHello)).

## Per-mechanism notes

### age-plugin-se (Apple Secure Enclave)

- **Platforms:** "To generate identities (private keys) and decrypt encrypted files, you need a Mac running macOS 14 (Sonoma) with a Secure Enclave processor. For encrypting files, you need macOS 14 (Sonoma), Linux, or Windows." The Windows binary needs Swift installed. ([README](https://github.com/remko/age-plugin-se)) Apple says the Secure Enclave needs "a Mac with the Touch Bar and Touch ID or with an M1 or later processor" ([Protecting keys with the Secure Enclave](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave)). An open issue asks for pre-2020 Intel support ([#24](https://github.com/remko/age-plugin-se/issues/24)).
- **Presence:** `--access-control` takes `none`, `passcode`, `any-biometry`, `any-biometry-and-passcode`, `any-biometry-or-passcode` (the default), `current-biometry`, and `current-biometry-and-passcode`. With `current-biometry`, "adding or removing a fingerprint stops the key from working". ([README](https://github.com/remko/age-plugin-se)) The `none` value creates an SE-bound key with no gate.
- **Cache:** None. The plugin builds one `LAContext` per process and never sets a reuse duration (`CryptoKitCrypto` in `Sources/Crypto.swift`). Apple's default for `touchIDAuthenticationAllowableReuseDuration` is 0, "meaning that Touch ID authentication isn't reused" ([Apple](https://developer.apple.com/documentation/localauthentication/lacontext/touchidauthenticationallowablereuseduration)). Asked for a gpg-agent-style cache, the maintainer replied: "age-plugin-se is stateless, just as age is. The underlying SecureEnclave does not support sessions ... and it's out of scope to implement something like this in this plugin" ([#19](https://github.com/remko/age-plugin-se/issues/19)). So each `sops -d` costs one prompt. Several key operations inside one plugin process probably share that process's context; this is inferred from the code, not documented.
- **Exportable:** No. "The private key is bound to the secure enclave of your machine, so it cannot be transferred to another machine." The identity file holds an encrypted key blob that only that Secure Enclave can use. ([README](https://github.com/remko/age-plugin-se)) Apple: "Not having a mechanism to transfer plain-text key data into or out of the Secure Enclave is fundamental to its security." ([Apple](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave))
- **Why a plain CLI can use it:** The plugin uses CryptoKit Secure Enclave keys and stores their blobs in its own identity file, not in the data protection keychain. So it avoids the entitlement and provisioning-profile requirement that the approval-gating research found for `SecAccessControl` keychain items. This is an inference from the code and from its distribution as a Homebrew CLI.
- **Recipients:** `--recipient-type se` (`age1se1...`, the default for now) needs the plugin wherever encryption happens. `tag` (`age1tag1...`) "use built-in support in age (>=v1.3.0), and don't require this plug-in to be installed to encrypt". "The default will change to `tag` in future versions." ([README](https://github.com/remko/age-plugin-se))
- **Maturity:** v0.2.1 released 2025-12-27; 257 stars; 6 open issues and pull requests combined. In August 2026 the maintainer answered a call for co-maintainers with "Yes, I'm still maintaining it" ([#22](https://github.com/remko/age-plugin-se/issues/22)). An open issue says Homebrew still ships an older version than 0.2.1 ([#14](https://github.com/remko/age-plugin-se/issues/14)), so `brew install` may not give `--recipient-type tag`. Someone already wraps it with SOPS for team secrets (`sopsy`, mentioned in [#19](https://github.com/remko/age-plugin-se/issues/19)).
- **Install:** `brew install age-plugin-se`, or a release binary that has to be trusted once in Finder ([README](https://github.com/remko/age-plugin-se)).
- **Recovery, new machine, CI:** The README advises keeping "an alternate backup key". Each new Mac adds a new recipient and needs a re-wrap. CI and Windows or Linux machines need the plugin to encrypt to `age1se1`, or `age-plugin-tag` for `age1tag1` (see SOPS integration).

### age-plugin-yubikey (YubiKey PIV)

- **Platforms:** Pre-built binaries for Windows, Linux, and macOS, plus Homebrew, Cargo, Arch, Debian, NixOS, and OpenBSD packages. "On non-Windows, non-macOS systems, you need to ensure that the `pcscd` service is installed and running." ([README](https://github.com/str4d/age-plugin-yubikey)) The v0.5.1 release ships only darwin and Windows archives; v0.5.0 also has a Linux tarball and a `.deb` ([releases](https://github.com/str4d/age-plugin-yubikey/releases)). It supports YubiKey 4 and 5 series only; the blue Security Key "will also not work (as it doesn't support PIV)".
- **Presence:** The defaults are PIN policy `once` and touch policy `always` (`DEFAULT_PIN_POLICY` and `DEFAULT_TOUCH_POLICY` in `src/builder.rs`; help text in `src/main.rs`). Yubico: with the `Cached` touch policy, "if more than 15 seconds have elapsed since the last time the YubiKey was touched, a touch is needed" ([Yubico](https://docs.yubico.com/yesdk/users-manual/application-piv/pin-touch-policies.html)). With `always`, every decryption needs a touch.
- **Cache:** Since 0.4.0 "The YubiKey PIV PIN and touch caches are now preserved across processes in most cases", so with PIN policy `once`, later calls "won't request a PIN entry" ([CHANGELOG](https://github.com/str4d/age-plugin-yubikey/blob/main/CHANGELOG.md)). The session ends on unplug, on use of another applet such as FIDO2, or on generating a new identity. Cache preservation "does not work for YubiKey 4 series". ([README](https://github.com/str4d/age-plugin-yubikey)) So under the defaults the PIN gate is per session, and the touch is the per-decryption gate. The plugin does not run an agent.
- **Touch UX:** The plugin no longer prints a touch reminder and leaves it to the client's "waiting on plugin" notice. Users report the process just seems to hang ([#154](https://github.com/str4d/age-plugin-yubikey/issues/154)). SOPS's plugin UI wires up age's `WaitTimer` (`pluginTerminalUI` in `age/tui.go`).
- **Exportable:** Yubico: "generated keys are non-exportable, for security reasons" ([Yubico PIV guide](https://developers.yubico.com/PIV/Guides/Generating_keys_using_OpenSSL.html)). The identity file only "contains information that an age client can use to figure out which YubiKey secret key should be used" ([README](https://github.com/str4d/age-plugin-yubikey)), so it is not a secret.
- **Recipients:** Today `age1yubikey1...`. Unreleased work switches the CLI and identity files to `age1tag1...`. Encrypting to those needs the binary on `PATH` "as `age-plugin-tag`", or a client with native support. ([CHANGELOG](https://github.com/str4d/age-plugin-yubikey/blob/main/CHANGELOG.md))
- **Maturity:** v0.5.1 (2026-04-08), 988 stars, 58 open issues and pull requests combined, recommended (starred) in [awesome-age](https://github.com/FiloSottile/awesome-age). Relevant open issues: PIN asked every time on some setups ([#144](https://github.com/str4d/age-plugin-yubikey/issues/144)), and a Windows SIM-card reader aborting reader enumeration ([#231](https://github.com/str4d/age-plugin-yubikey/issues/231)).
- **Install:** Buy hardware, install the plugin, run `age-plugin-yubikey` once. It changes a default PIN and management key for the user ([README](https://github.com/str4d/age-plugin-yubikey)).
- **Recovery, new machine, CI:** The same YubiKey works on every machine where it is plugged in, so "adding a machine" means copying the non-secret identity stub, with no re-encryption. A lost or broken key needs the recovery key or a second YubiKey enrolled as a backup recipient. CI needs the plugin binary (or `age-plugin-tag`) to wrap the data key for it. Whether the Linux binary starts without `libpcsclite` on a CI runner is unverified.

### age-plugin-tpm

- **Platforms:** Linux only. The transport opens `/dev/tpmrm0` through go-tpm's `linuxtpm` (`NewTPM` in `plugin/tpm.go`), and every release asset is a Linux build ([releases](https://github.com/Foxboron/age-plugin-tpm/releases)). The user needs permission on the device ([#22](https://github.com/Foxboron/age-plugin-tpm/issues/22), [#47](https://github.com/Foxboron/age-plugin-tpm/issues/47)). WSL2 has no TPM device; a feature request has been open since 2020 ([microsoft/WSL#5178](https://github.com/microsoft/WSL/issues/5178)).
- **Presence:** None. A TPM has no biometric or touch sensor. `--pin` adds an authorization value: the plugin asks for it through the client's `request-secret` ("Please enter the PIN for the key:"), or reads `AGE_TPM_PIN`. The README warns that environment variables "can be read from `/proc/$PID/environ`". ([README](https://github.com/Foxboron/age-plugin-tpm), `cmd/age-plugin-tpm/main.go`) TPM anti-hammering limits guessing. Windows configures TPM 2.0 "to lock after 32 authorization failures and to forget one authorization failure every 10 minutes" ([Microsoft: TPM fundamentals](https://learn.microsoft.com/en-us/windows/security/hardware-security/tpm/tpm-fundamentals)). On Linux the lockout parameters depend on how the TPM was provisioned (unverified for typical distros).
- **Exportable:** No. `CreateIdentity` sets `FixedTPM` and `FixedParent`, and the README says "Keys created on the TPM, sealed outside of it". The identity file holds a blob that only this TPM can load.
- **Recipients:** v1.0 prints `age1tag1...` recipients ([README](https://github.com/Foxboron/age-plugin-tpm)), which age 1.3+ can encrypt to without the plugin.
- **Maturity:** v1.0.1 (2026-01-24), 167 stars, 5 open issues, including one asking for "Clearer security guarantees" ([#33](https://github.com/Foxboron/age-plugin-tpm/issues/33)). Marked experimental in [awesome-age](https://github.com/FiloSottile/awesome-age).
- **What it buys KeyPick:** Exfiltrating `keys.txt` no longer works, because the identity is useless off this machine. But a same-user process can still decrypt silently when there is no PIN, or when the PIN sits in `AGE_TPM_PIN`.

### FIDO2 plugins

**age-plugin-fido2-hmac**

- **Design:** The README warns: "FIDO2 does not provide an API for asymmetric encryption; instead, this plugin uses the hmac-secret extension to protect an Age identity with your hardware key. For decryption, the identity is transferred to your computer's memory. If this identity is stolen from memory, it can be used without the token to decrypt past and future data meant for this identity." ([README](https://github.com/olastor/age-plugin-fido2-hmac)) The spec derives "an X25519 public key using the 32 byte hmac output as a private key", and in "separate identity" mode the recipient is a native X25519 `age1...` key ([spec v2](https://github.com/olastor/age-plugin-fido2-hmac/blob/main/docs/spec-v2.md)).
- **Presence:** The spec requires that "The secret key MUST only be generated with user presence (i.e. touching the authenticator)", with an optional PIN that "is not just an UI guard, but the token changes the secret". ([spec v2](https://github.com/olastor/age-plugin-fido2-hmac/blob/main/docs/spec-v2.md), [README](https://github.com/olastor/age-plugin-fido2-hmac)) On the token side, CTAP 2.1's `hmac-secret` processing says: "If "up" is set to false, authenticator returns CTAP2_ERR_UNSUPPORTED_OPTION". It then picks `CredRandomWithUV` or `CredRandomWithoutUV` from the UV bit, so a PIN-protected credential yields a different secret ([CTAP 2.1, §12.5](https://fidoalliance.org/specs/fido-v2.1-ps-20210615/fido-client-to-authenticator-protocol-v2.1-ps-errata-20220621.html)). systemd notes that some tokens don't let the presence requirement "be enabled or disabled for the requested operation" ([systemd-cryptenroll](https://github.com/systemd/systemd/blob/main/man/systemd-cryptenroll.xml)). Whether every token enforces presence for `hmac-secret` is unverified.
- **What one approval releases:** The long-term identity. A same-user process doesn't need the plugin. With the non-secret credential ID and salt from the identity file, it can run its own FIDO2 client, and one touch the user gives (plus the PIN, if one is required) yields the X25519 private key permanently. This is an inference from the design.
- **Platforms and install:** age ≥ 1.1.0 or rage, plus libfido2. "Windows builds are currently not enabled", yet v0.5.0 ships a `windows-amd64` archive, and on Windows "the command must be run as an administrator" ([README](https://github.com/olastor/age-plugin-fido2-hmac), [releases](https://github.com/olastor/age-plugin-fido2-hmac/releases)). Microsoft: when the WebAuthn APIs are in use, "browsers or applications don't have direct access to the FIDO2 transports" ([Microsoft: WebAuthn APIs](https://learn.microsoft.com/en-us/windows/security/identity-protection/hello-for-business/webauthn-apis)).
- **Maturity:** v0.5.0 (2026-05-11), 111 stars, "experimental until the version v1.0.0", marked experimental in awesome-age. Open issues include memory wiping of secrets ([#52](https://github.com/olastor/age-plugin-fido2-hmac/issues/52)).
- **Recovery, new machine, CI:** The token works on any machine. A native X25519 recipient means CI and other machines need no plugin to encrypt.

**age-plugin-fido2prf**

- "Since WebAuthn encryption is symmetric, there is no recipient encoding, only identities." It installs with `go install filippo.io/typage/fido2prf/cmd/age-plugin-fido2prf@latest`. ([typage README](https://github.com/FiloSottile/typage))
- Encrypting needs the token, so CI could not re-wrap a data key for it, and a new machine could not be added without the token present. That rules it out for KeyPick's recipient model.

Other hardware plugins listed in [awesome-age](https://github.com/FiloSottile/awesome-age) (age-plugin-tkey, age-plugin-trezor) were not reviewed.

### Windows Hello (`KeyCredentialManager` and the Passport key storage provider)

- **No age plugin:** None is listed in [awesome-age](https://github.com/FiloSottile/awesome-age), and GitHub repository and code searches for age plugins using `KeyCredentialManager`, the Microsoft Passport key storage provider, or Windows Hello returned nothing (2026-10-10). Microsoft-documented building blocks:
  - "When the user sets up Windows Hello ... The trusted platform module (TPM) generates and protects this private key. If the device does not have a TPM chip, the private key is encrypted and protected by software." ([Microsoft: Windows Hello for apps](https://learn.microsoft.com/en-us/windows/apps/develop/security/windows-hello))
  - `RequestSignAsync` causes "Windows to request the user's PIN or biometrics through Windows Hello. At no time will the developer have access to the private key of the user." The key is RSA, with SHA-256 and PKCS#1 signatures. ([same page](https://learn.microsoft.com/en-us/windows/apps/develop/security/windows-hello)) RSASSA-PKCS1-v1_5 signatures are deterministic ([RFC 8017, section 8.2](https://www.rfc-editor.org/rfc/rfc8017#section-8.2)), which is why KeePassXC can hash a signature into a stable AES key (approval-gating research).
  - "An application can never use the keys from another application" ([same page](https://learn.microsoft.com/en-us/windows/apps/develop/security/windows-hello)). The page is written for packaged apps. Whether an unpackaged CLI's keys are shielded from other same-user processes is unverified. KeePassWinHello and the ByteNess keyring open Passport keys by a name they construct, with no app identity check in their code (`WinHelloProvider.cs`, `winhello/passport.go`).
- **Two ways to build it:**
  1. *Per-use decrypt key (an age plugin).* Create an RSA key in the Passport provider with `NCRYPT_ALLOW_DECRYPT_FLAG` and wrap each file key to it; `NCryptDecrypt` raises the Hello prompt. KeePassWinHello does exactly this decrypt step (`NCryptDecrypt` with PKCS#1 padding), and the ByteNess fork does the same for aws-vault. One approval releases one file key. Both projects also set an `NgcCacheType` property to an "auth mandatory" flag. Microsoft's [key storage property list](https://learn.microsoft.com/en-us/windows/win32/seccng/key-storage-property-identifiers) does not document it, and the constant appears only in third-party code. Its effect is unverified.
  2. *Unwrap a software identity (a `SOPS_AGE_KEY_CMD` helper).* Use the KeePassXC sign-a-challenge pattern, or a Passport decrypt, to unwrap a stored X25519 identity and print it for SOPS. It is easier to build, but one approval hands the long-term identity to whichever process ran the helper.
- **Recipient format:** An RSA key fits no native age recipient type, so design 1 would use its own `age1<name>1...` recipient. CI and other machines would then need the plugin's recipient side, which is ordinary RSA-OAEP software that could build for Linux. Whether the Passport provider can hold a P-256 key-agreement key, which would allow `age1tag1` recipients, is unverified.
- **Cache:** Microsoft does not document whether Windows reuses a recent Hello gesture for later key operations (still open from the approval-gating research).
- **Recovery, new machine, CI:** The key is per machine and per user. A PIN reset destroys it: "Resetting the PIN means that all keys and certificates encrypted with the old key material will be removed." ([Microsoft: Windows Hello for apps](https://learn.microsoft.com/en-us/windows/apps/develop/security/windows-hello)) So the recovery key or another machine must always remain a recipient.
- **Other Windows mechanisms:** age-plugin-yubikey runs natively on Windows. FIDO2 `hmac-secret` needs administrator rights there. age-plugin-tpm has no Windows build. CNG "strong key protection" (`NCRYPT_UI_POLICY`) shows a dialog "as needed" ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/ncrypt/ns-ncrypt-ncrypt_ui_policy)); its per-use behaviour is undocumented and it was not pursued.

### DPAPI (the no-presence baseline)

- "Typically, only a user with the same logon credential as the user who encrypted the data can decrypt the data. In addition, the encryption and decryption usually must be done on the same computer." "A user with a roaming profile can decrypt the data from another computer on the network." ([CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata))
- The optional prompt flow "is deprecated and will be removed in **February 2027**" ([same page](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)).
- Any process running as the user can call `CryptUnprotectData`. Against the agent threat model, a DPAPI-wrapped `keys.txt` is equivalent to plaintext. It only protects against offline disk theft and other users.

### SOPS passphrase-protected identity (the knowledge baseline)

- SOPS 3.10.0 added "Support Age identities with passphrases" ([CHANGELOG](https://github.com/getsops/sops/blob/main/CHANGELOG.md)). SOPS asks gpg-agent for the passphrase, with a cache key derived from the file's hash, and falls back to a terminal prompt when gpg-agent isn't reachable (`unwrapIdentities` in `age/encrypted_keys.go`).
- With gpg-agent, the approval-gating research applies: any client of the agent reuses the cached passphrase for 600 s, and up to 7,200 s. Without gpg-agent, every `sops` run prompts.
- It runs everywhere, Linux and WSL included, with no hardware. Once unwrapped, it is still a software key.

### Plaintext `keys.txt` (today)

- `localAgePublicKey` in `ts/src/lib/vault.ts` and the setup helpers in `ts/src/commands/setup/utils.ts` read the identity from the SOPS default location. Any same-user process can read it or run `sops -d`. This is the gap the ticket exists to close.

## WSL: reaching a Windows-side key

- **Run the Windows plugin through interop.** age-plugin-yubikey documents this: install it on the Windows host, install an age client in WSL, and make sure `age-plugin-yubikey.exe` is on the WSL `PATH` ([README](https://github.com/str4d/age-plugin-yubikey)). The plugin protocol runs over stdin and stdout, which interop pipes. Microsoft: Windows tools run from WSL "Run as the active Windows user", and "must include the file extension" ([Microsoft: working across file systems](https://learn.microsoft.com/en-us/windows/wsl/filesystems)). age looks for the plugin as `age-plugin-<name>` without an extension (`openClientConnection` in age's `plugin/client.go`), so a Linux SOPS probably needs a shim named `age-plugin-yubikey` that runs the `.exe` (unverified end to end). A KeyPick-built Windows Hello plugin could be reached the same way, and its prompt would appear on the Windows desktop.
- **Pass the token into WSL with usbipd-win.** `usbipd bind` "requires administrator privileges". "As long as the USB device is attached to WSL, it cannot be used by Windows." It needs WSL 2 and a kernel of 5.10.60.1 or later. ([Microsoft: connect USB devices](https://learn.microsoft.com/en-us/windows/wsl/connect-usb)) The Linux plugin then needs `pcscd` or libfido2 inside WSL.
- **A `SOPS_AGE_KEY_CMD` that calls a Windows helper.** This works, but it pipes the long-term identity into WSL on each call (see the Windows Hello notes).
- **TPM:** Not reachable from WSL2 ([microsoft/WSL#5178](https://github.com/microsoft/WSL/issues/5178)).
- **Same-user parity:** Any WSL process can start Windows binaries as the active Windows user, so a Windows-side key is exactly as reachable from WSL as from any Windows process of that user. The gesture is the only gate.

## SOPS integration

- **Versions:** 3.10.0 (released 2025-03-30) added "Age plugin support", "Allow to set the `SOPS_AGE_KEY_CMD` environment variable to an executable that returns Age keys", and passphrase-protected identities. 3.11.0 loads identities "from all locations". 3.12.0 added hybrid post-quantum identities, passes `SOPS_AGE_RECIPIENT` to `SOPS_AGE_KEY_CMD`, and adds `SOPS_AGE_SSH_PRIVATE_KEY_CMD`. The latest release is 3.13.3 (2026-07-23). ([CHANGELOG](https://github.com/getsops/sops/blob/main/CHANGELOG.md), [releases](https://github.com/getsops/sops/releases)) Before 3.10, SOPS rejected plugin recipients with `invalid type "age1se"` ([age-plugin-se #11](https://github.com/remko/age-plugin-se/issues/11)).
- **Recipients:** A plugin recipient goes into `.sops.yaml` (or `--age`) exactly like an X25519 one. `parseRecipient` in `age/keysource.go` sends any `age1...` string with more than one `1` (`age1se1...`, `age1yubikey1...`, `age1tag1...`) to `plugin.NewRecipient`, sends `age1pq1...` to the hybrid parser, and treats the rest as X25519. For example:

  ```yaml
  creation_rules:
    - path_regex: vault\.yaml$
      age:
        - age1...            # recovery key (X25519)
        - age1...            # GitHub Actions key (X25519)
        - age1se1...         # a Mac's Secure Enclave key
        - age1yubikey1...    # a YubiKey slot
  ```

- **Identities:** Lines starting with `AGE-PLUGIN-` in `SOPS_AGE_KEY`, `SOPS_AGE_KEY_FILE`, the output of `SOPS_AGE_KEY_CMD`, or the default `keys.txt` become plugin identities (`parseIdentity` in `age/keysource.go`). The default locations are `%AppData%\sops\age\keys.txt` on Windows; on Linux, `$XDG_CONFIG_HOME/sops/age/keys.txt`, falling back to `~/.config`; on macOS, `$XDG_CONFIG_HOME` falling back to `~/Library/Application Support` ([SOPS docs: age](https://getsops.io/docs/usage/identities/age/)). For the Secure Enclave, YubiKey, and TPM plugins the identity line is a handle or a hardware-wrapped blob, not a usable secret. So it can sit in a plain file without reopening the hole.
- **Plugin lookup:** The age client searches `PATH` for `age-plugin-<name>`, and "Paths relative to the current working directory MUST NOT be searched" ([C2SP age-plugin](https://c2sp.org/age-plugin)). The plugin is needed on *every* machine that encrypts to that recipient, not only where decryption happens. Go's `exec.LookPath` searches "following the conventions of the host operating system"; on Windows the file "must have an extension named by the PATHEXT environment variable" ([Go `os/exec`](https://pkg.go.dev/os/exec#LookPath)). So `age-plugin-yubikey.exe` is found as `age-plugin-yubikey`, and `.exe` plugins work natively there.
- **Tagged recipients:** age 1.3.0 can encrypt natively to `age1tag1...` and `age1tagpq1...` ([age v1.3.0 release](https://github.com/FiloSottile/age/releases/tag/v1.3.0)). SOPS does not yet parse them natively, although its main branch already depends on age 1.3.1 (`go.mod`). They go through plugin lookup and need an `age-plugin-tag` binary, which age ships as a compatibility plugin in `extra/age-plugin-tag` ([source](https://github.com/FiloSottile/age/tree/main/extra)). A pull request to add native support, getsops/sops#2266, has been open since 2026-07-31.
- **Prompts:** SOPS answers plugin `msg`, `request-secret`, `confirm`, and wait notices with age's terminal UI (`pluginTerminalUI` in `age/tui.go`). That UI reaches "the terminal ... directly through /dev/tty or CONIN$/CONOUT$" (age's `plugin/tui.go`). So a PIN prompt reaches the user's terminal even when KeyPick captures `sops` stdio, and it fails when no terminal exists. Touch ID, Hello, and touch-only YubiKey prompts don't need the terminal.
- **`SOPS_AGE_KEY_CMD`:** The command is split with shell-like rules and run without a shell, with `SOPS_AGE_RECIPIENT` set to the recipient of the master key being decrypted. Its stdout is parsed as identities, one per line. (`loadIdentities` and `getOutputFromCmd` in `age/keysource.go`) Identities are loaded lazily per master key, so the command may run once for each recipient that SOPS tries. A gated helper should print nothing for recipients that aren't its own, or the user will see several prompts (inferred from the code). It returns *identities*, so a gate inside it releases the long-term key, or a plugin handle, to the caller.
- **Data keys:** Each SOPS file has its own data key, which age wraps once per recipient. `sops -d` unwraps it once per file. `sops updatekeys` unwraps it and re-wraps it for the new recipient set. KeyPick's `save()` in `ts/src/lib/vault.ts` re-encrypts `vault.yaml` from a plaintext temp file with `sops --encrypt`, which creates a new data key wrapped to every recipient.

## Implications for KeyPick

These are options, not a recommendation.

### What changes regardless of option

- **SOPS version:** It must be ≥ 3.10.0 everywhere: in `SOPS_VERSION` in `ts/src/commands/setup/prerequisites.ts` (3.9.4 today), and in the vault-sync workflow (`.github/workflows/vault-sync.yml` and the copy in `ts/src/assets/vault-sync.yml`, both 3.9.1 today).
- **`verify()` stops being the gate.** The plugin's prompt is the real one, so `requireBio` in `ts/src/main.ts` would add a second prompt in front of it. Every `sops -d` costs one approval, so:
  - `load()` costs one approval per command.
  - `env pull` costs one per env file.
  - `canDecryptVault` in `ts/src/commands/setup/utils.ts` costs one just to probe.
  - Local `sops updatekeys` in the join and recovery flows costs one per file.
- **Writers need every recipient type.** `save()` wraps a fresh data key to every recipient, so every machine that adds a secret needs recipient-side support for every plugin type in `.sops.yaml`. A plugin binary per type, or one `age-plugin-tag` if every hardware recipient is `age1tag1`. On a Windows machine, encrypting to an `age1se1` recipient means installing Swift.
- **Recipient parsing:** `readPublicKey` and `localAgePublicKey` look only for a `# public key:` comment.
  - age-plugin-se identity files have that line.
  - age-plugin-tpm writes `# Recipient:`.
  - age-plugin-yubikey writes `#    Recipient:` (its `yubikey-identity` template).

  The `age1` prefix checks in `join.ts` and `addRecipient` already accept plugin recipients.
- **Habitual approval:** No mechanism stops a user from approving a prompt that an agent triggered. Mechanisms that release one file key bound the damage to that file's data key. Mechanisms that release the long-term identity don't.

### Per-platform options

| Platform | Option | Gesture on each decryption | One approval releases | Silent same-user decrypt | Main cost |
| --- | --- | --- | --- | --- | --- |
| macOS | age-plugin-se, `any-biometry` or `current-biometry` (or the default, which allows passcode) | Touch ID, or the login passcode if allowed | One file key | No | Plugin install; machine-bound key; `age1se1` needs the plugin (or `age-plugin-tag`) on every writer and in CI |
| macOS, Windows, Linux | age-plugin-yubikey, touch `always` | Physical touch (PIN once per session) | One file key | No; with touch `cached`, yes for 15 s | Hardware per user; touch has no on-screen cue; `pcscd` on Linux |
| Windows | New KeyPick age plugin on a Passport decrypt key | Hello face, fingerprint, or PIN | One file key | No, if the `NgcCacheType` "auth mandatory" flag works as assumed (unverified) | KeyPick writes, signs, and maintains a plugin plus a Linux recipient-side build for CI |
| Windows | Hello-unwrapped identity via `SOPS_AGE_KEY_CMD` | Hello gesture per helper call | The long-term identity | No, but one approval is permanent | Simpler build; weakest guarantee of the gated options |
| Windows | DPAPI-wrapped `keys.txt` | None | n/a | Yes | Meets nothing in the threat model |
| Linux | age-plugin-fido2-hmac | Touch (plus optional PIN) | The long-term identity | No | Experimental plugin; libfido2; FIDO2 key |
| Linux | age-plugin-tpm with `--pin` | None (knowledge: PIN) | One file key | Only if the PIN leaks, for example through `AGE_TPM_PIN` | Linux only; TPM device access; the PIN is not presence |
| Linux, WSL | Passphrase-protected identity (SOPS-native) | None (knowledge) | The long-term identity | Yes, while gpg-agent caches it | No hardware; gpg-agent cache is shared |
| WSL | Windows-side plugin through an interop shim (YubiKey today; a Hello plugin if built) | Same as the Windows option | Same as the Windows option | No | Shim naming; prompt shows on the Windows desktop |
| WSL | YubiKey or FIDO2 token through usbipd-win | Touch | As for the Linux plugin | No | Admin `bind`; token is unavailable to Windows while attached |

Linux has no OS biometric keystore. polkit and fprintd only return pass or fail (approval-gating research). On Linux, per-decryption *presence* means a USB token.

### Recovery key

- Machine-bound keys (Secure Enclave, TPM, Hello) can't be backed up, so the software recovery key that `ts/src/commands/setup/recovery.ts` creates stays essential. It must stay a recipient of every file.
- It is a passphrase-encrypted X25519 key kept offline. It has no presence gate, but it isn't reachable by an agent while it stays off the machine.
- SOPS ≥ 3.10 can read a passphrase-protected identity file directly. So the recovery instructions could point `SOPS_AGE_KEY_FILE` at the encrypted file instead of writing `temp_key.txt` in plaintext. Not tested here: whether SOPS accepts the binary (non-armored) output that `age -e -p` produces in `recovery.ts`.
- A second YubiKey enrolled as a recipient is a hardware alternative or addition.

### Adding a new machine

- **Machine-bound keys:** The new machine generates its own recipient, and someone who can already decrypt runs `sops updatekeys`. That is the deferred path in `ts/src/commands/setup/join.ts`. On a presence-gated machine it costs one approval per file.
- **Roaming tokens (YubiKey, FIDO2):** The new machine only needs the plugin and the non-secret identity stub. The recipient set doesn't change, and nothing is re-encrypted.

### GitHub Actions re-encryption workflow

- **Today:** CI holds a plaintext X25519 key in the `SOPS_AGE_KEY` secret and writes it to `keys.txt` on the runner. `sops updatekeys` must decrypt each data key, so CI can read every secret.
- **CI secret exposure:** GitHub: "Any user with write access to your repository has read access to all secrets configured in your repository", and "automatic redaction is not guaranteed" ([GitHub Actions security guide](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)). An agent that can push to the vault repository could add a workflow step that leaks the CI key, which bypasses every per-machine gate.
- **Ways to handle CI:**
  - **C1. Keep CI re-encryption, ungated.** Install SOPS ≥ 3.10 and, for each plugin recipient type, the plugin's Linux build or `age-plugin-tag`. Accept that CI is a no-presence path.
  - **C2. Gate the CI secret with a GitHub environment that has required reviewers** (and "Prevent self-review"). "Workflow jobs that use this environment can only access these secrets after" the rules pass. That makes a GitHub approval CI's presence gate. GitHub Free can configure environments only for public repositories; GitHub Pro and Team can configure them for private ones. ([GitHub: environments](https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-deployments/managing-environments-for-deployment))
  - **C3. Drop CI re-encryption** and re-wrap on a machine that already has access, paying one approval per file. CI then holds no key.
  - **Under any option:** Recipients that encrypt natively (X25519, the FIDO2 "separate identity" recipient, or `age1tag1` once SOPS supports it) keep CI's toolchain smallest.

## Unverified or open

- What the Passport provider's `NgcCacheType` "auth mandatory" property does, and whether Windows otherwise reuses a recent Hello gesture. Microsoft doesn't document either.
- Whether a Passport or `KeyCredentialManager` key created by an unpackaged CLI can be opened by another same-user process (assumed yes).
- Whether the Passport provider supports P-256 key agreement, which would allow `age1tag1` recipients for a Hello plugin.
- Whether every FIDO2 token refuses `up=false` for `hmac-secret`, as CTAP 2.1 requires.
- Whether a Linux SOPS in WSL can run `age-plugin-yubikey.exe` through a shim named without `.exe`; this was not tested.
- Whether the Linux age-plugin-yubikey binary runs on a CI runner without `libpcsclite`, and whether age-plugin-se's Linux build needs a Swift runtime.
- TPM dictionary-attack defaults on common Linux distributions.
- Whether SOPS reads a binary, non-armored passphrase-encrypted identity such as `recovery_key.age`.
- The exact prompt text each OS shows, and whether it names the original caller or only the plugin.
- Aside, outside this ticket: on macOS, SOPS's default identity path is `~/Library/Application Support/sops/age/keys.txt` unless `XDG_CONFIG_HOME` is set. KeyPick's `localAgePublicKey` and setup helpers use `~/.config/sops/age/keys.txt`. Worth checking separately.
